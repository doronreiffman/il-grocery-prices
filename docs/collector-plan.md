# Collector Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Grade:** portfolio project; the collector is held to production grade because a missed morning cannot be recovered.

**Goal:** a scheduled Lambda in il-central-1 that stores, every morning and write-once, each in-scope chain's store list, full price and full promotions files and the update files listed at that moment, and emails the owner only when a listed file is not stored, a chain is stopped, or a run fails.

**Architecture:** one Lambda, invoked by EventBridge Scheduler once per chain (and per file type for Shufersal) in three modes: `main`, `retry`, `check`, plus a manual `unblock`. Each chain has a source adapter (Shufersal, NCR "Published Prices", Carrefour) behind one interface; a shared run loop selects that day's files, downloads one at a time, validates, and writes them byte for byte to an Object Lock bucket with `IfNoneMatch="*"`, then writes a manifest. The check run compares what was listed against what the bucket holds. Patterns follow `/Users/doronreiffman/Projects/flights-archive` (`src/collector/store.py`, `handler.py`, `template.yaml`, `scripts/mutation_check.py`, `.github/workflows/ci.yml`).

**Tech Stack:** Python 3.13 (stdlib `urllib`, `http.cookiejar`, `html.parser`, `xml.etree`, `gzip`), boto3 (provided by the Lambda runtime), AWS SAM, pytest, pytest-cov, cfn-lint.

**Spec:** `docs/collector.md` (approved by the owner 2026-10-31). Read it first; this plan argues from it.

Never a browser User-Agent, another IP, a proxy, or another route. Exception: a 403 from Shufersal's file host (`pricesprodpublic.blob.core.windows.net`) at or after the link's `se=` expiry time means re-read the listing for a fresh link, once.

- Keys: raw `raw/chain=<slug>/date=YYYY-MM-DD/<file name as published>`; a different body under a stored name goes to `<that key>.<first 12 hex of its SHA-256>`; manifests `manifests/date=YYYY-MM-DD/<slug>-<run id>.json`; check records `checks/date=YYYY-MM-DD/check-<run id>.json`; latch `state/<slug>.json`.
- Every raw, manifest and check write: `IfNoneMatch="*"`, `ObjectLockMode="GOVERNANCE"`, retain until now + 3650 days, `ChecksumAlgorithm="SHA256"` (flights-archive `store.py` `_put_locked`). Retention is set per object, not as a bucket default, so the state files stay plain, overwritable puts; the effect on stored files is the spec's ten-year governance lock.
- A run collects the current Israel calendar date (`zoneinfo` `Asia/Jerusalem` at run time); a file belongs to the date in its name, never to the time it was fetched. Every datetime is time-zone aware; never a naive `astimezone()` (this Mac runs on Asia/Jerusalem and CI on UTC, so a naive conversion passes in CI and is wrong here: flights-archive learned this).
- User-Agent `il-grocery-prices/<version> (+<repo URL>; <contact email>)`, from the deploy parameter `UserAgent`; the code refuses one without `+https://` and `@`. The owner's email, the health-check URL and any session token never go in the repo.
- One request at a time per chain; 0.5 s pause between files; at most one retry per file inside a run.
- Schedules, time zone `Asia/Jerusalem`: main from 06:30, retry from 09:30, check 10:00; per-chain invocations staggered 5 minutes apart; `MaximumRetryAttempts: 0` on the function's async config (Scheduler invokes asynchronously); schedules `DISABLED` by default through a `ScheduleState` parameter.
- Lambda: python3.13, arm64, 512 MB, 900 s timeout; a run stops downloading when under 60 s remain and records the rest as not attempted.
- The role may `s3:PutObject`, `s3:GetObject`, `s3:ListBucket` on the bucket (raw/, manifests/, checks/, state/) and `sns:Publish` on the alert topic; never `s3:DeleteObject*` or `s3:PutObjectRetention` beyond what a put needs.
- Fixtures under `tests/fixtures/` keep each portal's real structure (tags, attributes, layout, file names) with at most three items per file and synthetic prices, names and barcodes; signed-URL `sig=` values, cookies and CSRF tokens are scrubbed. Raw data is never published.
- Every component has tests; every rule gets a mutation in `scripts/mutation_check.py`; coverage floor 95% on `collector`; CI runs pytest, the mutation check and `cfn-lint --regions il-central-1`.
- No dependency younger than one month; pin versions.
- Docs in plain words; no "we".

## Review Focus

1. **A listing that parses to zero rows** (portal changed its page) must fail the run with "listing unreadable" and email, never read as "nothing published today". Test in Task 5 (`test_zero_rows_is_unreadable`) and Task 9 (`test_failed_run_alerts`).
2. **Time running out mid-chain**: the run stops when under 60 s remain, stores nothing half-written, writes its manifest with the rest as not attempted, and the retry run finishes the job. Test in Task 8 (`test_stops_before_timeout_and_records_not_attempted`).
3. **Shufersal link expiry vs a real block**: a 403 from the blob host after `se=` refreshes the link once; before `se=`, or from the listing host, it latches. Test in Task 5 (`test_expired_link_refreshes`, `test_403_before_expiry_blocks`).
4. **Old files in a listing**: closed stores' months-old files and yesterday's files are not selected and never count as "listed but not stored". Test in Task 8 (`test_only_that_days_files_selected`).
5. **Same-day re-run**: an identical body under a stored name is `EXISTS` (no conflict copy, no error); only a different body makes a conflict copy. Test in Task 7 (`test_identical_body_is_exists`, `test_different_body_gets_hash_suffix`).

- [ ] **Step 1: Write the failing tests:**

Where the design left room, the build decided; those decisions are part of the rule below.
  - **Page records.** A Shufersal run's manifest holds `pages`, one record per listing page it read, in the order read: `kind`, `page`, `rows`, `first` and `last` (the first and last file name on the page as listed, any date), `last_page` (the last page the page's pager names, null when it names none), `seconds` (the request's time, rounded to 0.1 s, the 0.5 s pause before it included, except on the run's first request, which has none), `in_order`, and `taken_through` (the last name the run took from the page, or the page's last name once the run took the last row the page gave; null when it took none). Other chains' manifests hold an empty `pages`. Each page also gets a log line at INFO, `shufersal PriceFull page 7 of 21: 20 rows in 41.2 s`, the count being the last page this run's page 1 of the kind named (`?` before the run has read that page 1). A page is in order when its names are in order and, if the page read just before it is the one numbered one less, its first name sorts at or after that page's last name. Pages read out of number order (a detour, page 1 after it, a step back) are not compared. A page out of order is recorded, and the run reads on.
  - **Where a run starts.** Before its listing, a Shufersal run lists the day's earlier Shufersal manifests and reads each. A failed read fails the run as an unexpected error (the manifest is still written), with no fall-back to a fresh pass. Blocked runs are left out, as the check leaves them out. For each kind: with no usable record (no earlier run took a name of the kind and it is not read in full, as with manifests from before page records that ended with an error; or a page of the kind recorded out of order that day, a blocked run's included), the run starts at page 1 with no detour, as before. Read in full, it starts a fresh pass at page 1, after a detour to each failed file's page except page 1. Not read in full, it resumes: page 1, then the page of the furthest name the earlier runs took (the larger page when two records hold it) again, for one page of overlap, or the last page when the pager now names an earlier one. While that page is past page 2 and its first name sorts after the furthest name, the run steps back a page: files that sorted before that name left the list, so it moved to an earlier page. (Files newly listed before it push it to a later page instead; reading on from the resume page still reaches that name and the names after it, with no step back.) A page stepped back from gives no rows; the run then reads on to the last page. A resume detours only to pages before the resume page, and a resume whose furthest name is on page 1 is a fresh pass that keeps its detours. A day not read in full only because of a gap between blocks still resumes at the furthest page. A failed file is a name an earlier run (not blocked) listed that the day has not stored; its page is that run's page whose first name and last name taken it falls between, and a detour reads that page once, before page 1.
  - **Read in full, across runs.** The runs that count for a kind are the chain's runs that day, main or retry, that cover it and were not blocked, whatever they ended with: a run that stopped on time or on an error counts for the pages it read. A counted run whose manifest holds no page records (other chains', and Shufersal's before this ruling) reads its kinds in full when it ended with no error, as R36 read it. The pages a run took a row from, in the order read, form blocks. A block ends where the next page's number is not one more, and after a page the run took only part-way, even in the middle of a run. A page the run took no row from is left out: one stepped back from, or one that gives no row because every name on it is unreadable. No run takes a row from such a page, so its block ends there and the day reads as not in full: an alert, which is right, since the portal changed. A block covers the names from its first page's first name to the last name taken from its last page. A block that starts at page 1 also covers everything before it; one that ends at the last page the run's own page 1 named (page 1 when that page names none; a run that did not read page 1 has no such block), with that page's last row taken, also covers everything after it. The kind is read in full when the counted runs' blocks, taken from the front, join up with no gap to past the last name. Joining needs every page of the kind recorded that day to be in order, blocked runs' pages included. When one is not, joining is off: a run without page records that ended with no error and was not blocked still counts, and a run with page records counts only when one of its blocks runs from page 1 to an open end: a whole pass, even one after a detour.
  - **R36 as amended.** A retry run whose only error is the time stop (`stopped: under 90 s left`) is not a failed run when each kind it covers was read in full that day (its own pages included), every name it listed was listed by another run that read the name's kind, and the chain has nothing missing. A run read the kind, for this, when it read the kind in full on its own, or when, with the retry's own pages left out, the other runs' pages join up into a full reading and one of its blocks carries that reading's end further than the blocks joined before it (the runs `read_in_full` names; blocks are joined from the front of the list, the furthest-reaching first among those that start together). A run vouches only for names of a kind it read (the kind read from the name, as R35 reads it). So a run that read only part of the list vouches only when its pages carry the joined reading further than the pages joined before them; a part that the pages joined before it already cover vouches for no name (a fresh pass that stopped on page 5 of a list another run read whole), nor does any part when the other runs' pages do not join up into a full reading without the retry's; the retry never vouches for its own names.
  - **The alert and the record.** A full kind the chain collects whose pages, recorded that day, do not join up is a failed run too. The failed alert then adds, for example, `the PriceFull list was not read in full: pages 17 to 21 never read`, naming apart the pages a run took only in part (`page 19 read in part`), and, when joining was off, the page out of order and its run. The sentence goes only for a kind with page records that day, and never when a retry run was blocked (the stopped alert covers it). The check record holds, per chain, `read_in_full`: for each full kind the chain collects, in the manifests' order, the ids of the runs without page records that ended with no error and were not blocked, and of the runs whose pages make up the joined full reading (a run that adds nothing to it, such as a second whole pass, is not named), or, with joining off, of every whole pass; null when the kind was not read in full.

  Why: every run read the list from page 1, since a download link expires 30 minutes after its page is served, and on a slow morning no 15-minute run reads a full kind's 21 pages (the design's "Why"). On 2026-11-03 about 77 stores' PromoFull were never listed. On 2026-11-05 about 103 stores' PriceFull and 110 stores' PromoFull were never listed: every main run of a full kind stopped on time, both full kinds' retries ended when page 2 passed the 60 s socket timeout, and the check reported one missing file, since `missing` covers only names some run listed. In every Shufersal run from 2026-11-03 to 2026-11-05, each run's names were in file-name order and each run's list was the start of the longest run's list for that kind and day. That order is what lets a run pick up where another stopped and the check join pages across runs; the per-page order check guards it. On 2026-11-05's shape the second run spends its time on pages 12 to 21 instead of 1 to 16 (the design's replay: expected, not measured; `tests/test_replay.py`).

  Cost if wrong: the name order is observed, not promised by Shufersal; a page out of order turns resuming and joining off for that kind and day, and the runs read from page 1 as before. A file published, after its part of the list was read, into a part only an earlier run covered is not collected until a fresh pass reaches it; if none does, it is never collected and sends no email (R36 accepted the same). Each resumed run spends one page on page 1. A gap between blocks is not read again that day: the next runs resume at the furthest page, not at the gap, so a file only the gap holds is not collected, though the alert names the gap. A retry that resumes, takes the list to its last row and then stops on time still alerts, though the day was read in full and nothing is missing: a false email on such a morning.

- Ruling R38 (2026-11-06, the owner's choice of fix, design `docs/shufersal-page-retry.md`; reopens the resume design's non-goal "no retry of a single slow page"): a Shufersal listing page whose request times out is asked for again, up to two more times, ten seconds apart, while the run has time, and every try is on the record. Where the design left room, the build decided; those decisions are part of the rule below.
  - **Which requests.** Every request for a Shufersal listing page: a kind's pages (Stores included), detours, steps back, and the expired-link refresh, which reads the category again for a fresh link. They all go through one function, `_read_page` (reached through `_pages` and `_PageReader`), and the tries live in `_page_body`, which it calls.
  - **Which failures.** Timeouts only. `Http` raises `HttpTimeout`, an `HttpError`, when a request's socket wait passed: a `TimeoutError`, or a `URLError` whose reason is one. Any other `HttpError` (a 5xx, a dropped connection, a cut-short body), a block (`Blocked`, which still stops the chain) and a page that was served but does not read (`ListingUnreadable`) are raised at once, whatever the try. `Http` still never retries, and file downloads keep their one retry (`ATTEMPTS = 2`).
  - **The tries and the pause.** Three tries in all (`PAGE_TRIES = 3`): the first, and up to two more, each after one that timed out. Before a second or third try the adapter asks the run's time check, pauses 10 s (`RETRY_PAUSE = 10.0`), asks the time check again, then sends the request; the first try asks the time check and sends, with no pause. (The design's Call 2 had the pause first and one time check after it; the check before the pause was added after the final whole-branch review on 2026-11-06, for the owner to confirm: `docs/shufersal-page-retry-plan.md`, "Deviations".)
  - **Time between tries.** When either time check before a later try finds under 90 s left, no pause or further request follows, and the run ends with exactly `stopped: under 90 s left`, as any time stop does (R36 matches that text exactly). The `OutOfTime` text names the try (`before try 2 of page 7 of the PriceFull listing`; before a first try it stays `before page 7 of the PriceFull listing`), but on the listing path the run loop records only the time stop; in a refresh the text is part of the file's failure, as before. The pause is taken only with time to spare, so the invariant of the 2026-11-01 Task 11 entry in "Deviations" (`MIN_TIME_LEFT` above the longest wait plus the manifest write) still holds: the longest span between a passing time check and the manifest write is one timed-out try of about 60 s, so the manifest is written with at least about 30 s left, as before this ruling. With only a check after the pause, a timed-out try that left under 10 s (urllib's 60 s wait applies to each socket step, so a slow connect and a passed read wait add up) would be followed by a pause that could outlast Lambda's limit, and no manifest would be written.
  - **When every try fails.** The adapter raises an `HttpError` naming the kind, the page and the tries, chained from the last timeout, and the run ends with `listing failed: <kind> page <n> timed out on 3 tries: <the last try's error>`, for example `listing failed: PriceFull page 7 timed out on 3 tries: GET https://prices.shufersal.co.il/FileObject/UpdateCategory failed: The read operation timed out`. The page has no page record, as a timed-out page had none before. In a refresh the adapter's text, without `listing failed: `, is the file's failure, and the download's second attempt reads the refresh again, bounded by the time rule.
  - **The record.** A page record gains `tries`: the requests it took to read the page, 1, or 2 or 3 when earlier tries timed out. Its `seconds` stays the successful request's time (Http's 0.5 s pause included, the retry pause and the failed tries left out), so page times stay comparable with 2026-11-06's. The manifest gains `timeouts`: one entry for every timed-out try of the listing, in the order reported, with `kind`, `page`, `attempt` (the try's number, from 1) and `seconds` (how long the try waited, Http's pause included), whatever followed it: a later try that read the page, the time stop, a third timeout, or a later try that failed another way (a 500 or a block, raised at once, its own error the run's). The adapter reports each through `on_timeout`, beside `on_page`, before any further try of the page; `timeouts` is empty on a run with no timed-out try and on every other chain's run. A refresh's tries are logged, not listed. Each timed-out try gets a WARNING line from the adapter, `shufersal PriceFull page 7: try 1 of 3 timed out after 60.5 s; again in 10 s`, ending "again in 10 s" only when another try follows: after a third try, and after a try that left the run under 90 s (the adapter asks the time check before the pause, then writes the line), it ends at the seconds. The page's INFO line gains ` (try n)` when the page took more than one try: `shufersal PriceFull page 7 of 21: 20 rows in 45.0 s (try 2)`.
  - **The check unchanged.** It reads neither `tries` nor `timeouts`, and its record gains no field; a manifest from before this ruling, with neither, reads as before. R36 and R37 apply as before: a page read on a later try joins as a page read on its first, and a page whose every try failed is a page never read, named among the pages never read in the alert. A retry run whose listing page failed every try alerts with its error, as the resume design's Call 1 has it: `retry run 074536Z-retry-5e4c (PriceFull) ended with: listing failed: PriceFull page 1 timed out on 3 tries: …`.
  - **Where the design left room.** The names: `HttpTimeout`, `PAGE_TRIES`, `RETRY_PAUSE`, `PageRead.tries`, `PageTimeout` (with `kind`, `page`, `attempt` and `seconds`: `try` is a Python keyword), the callback `on_timeout` and the manifest's `timeouts`. The texts above. The adapter logs each failed try, not the run loop: the line needs `PAGE_TRIES` and `RETRY_PAUSE`, which are the adapter's, and the refresh has no callback. A refresh's failed tries are logged and not listed in `timeouts` (the owner accepted this reading on 2026-11-06): the refresh reports no page, a download has no callback, and an entry from a refresh could not be told from a listing page's. The adapter takes its pause through a `sleep` given to its constructor, `time.sleep` by default, as `Http` does. The 2026-11-06 replay joins `tests/test_replay.py`, beside 2026-11-05's.

  Why: 2026-11-06, the resume's first morning (the design's "Why"): of about 39 Shufersal page requests, 6 passed the 60 s socket wait, and each ended its run with 5.5 to 14 of its 15 minutes unused; pages of 59.0 s and 60.0 s were read that morning, just inside the wait. PriceFull reached page 6 of 22, 117 of 417 stores. A retry wins the page that hovers at the edge of the wait, which before this ruling cost its run the rest of its time.

  Cost if wrong: a page read on its second try in 50 s costs its run 120 s, two pages' time for one. A slow portal gets up to two more requests a page, 10 s apart, one at a time as always. A slow spell still ends the run, about 140 s later than before (the 04:30Z and 04:45Z runs both died on page 1, fifteen minutes apart). A 5xx or a dropped connection is never asked again and shows in the run's error the first time. A refresh's tries show in the log only.

- Ruling R39 (2026-11-07, the owner's decision of 2026-11-05 and design `docs/update-files.md`, approved 2026-11-06; amends R29): the collector also collects the chains' update files (`Price`, `Promo`) through the day, in poll runs on a switch of their own, and each morning's check judges the day before's update files. Where the design left room, the build decided (`docs/update-files-plan.md`, "Where the design leaves room, this plan decides"); those decisions are part of the rule below.
  - **The poll mode.** A third collecting mode, `{"mode": "poll", "chain": "<slug>", "kinds": [...]}`, runs the run loop as `main` and `retry` do: the day's names of the kinds asked for, names stored that day skipped, one download at a time, each file stored write-once, a manifest written whatever happened. Its run id is `<HHMMSS>Z-poll-<4 hex>`; its day is the Israel date when it starts, and a file belongs to the day in its name. A poll event must name its kinds (a default would hand Shufersal both update kinds in one run): without them the handler refuses it (`a poll event names its kinds`) before any run. An unknown mode's error now names five: `main, retry, poll, check or unblock`.
  - **`Chain.polled`.** The update kinds a chain's poll runs read, in `KINDS` order: `("Price", "Promo")` for Rami Levy, Osher Ad, Carrefour and Yochananof, and empty for Shufersal until its passes are scheduled (rollout step 3). `Chain.kinds` keeps its meaning, the kinds the morning collects (Shufersal's `Stores`, `PriceFull`, `PromoFull`). Those names are never stored by the run nor put in `listed`: Osher Ad's 23:50 poll, still running after midnight, counts the next day's names and leaves them to the next morning's main run. A Shufersal poll's manifest carries `pages` and `timeouts`, as every Shufersal run's does (R37, R38).
  - **The passes.** An update kind is read several times a day, so its day is cut into passes, each read in full or not as R37 reads a day (`collector.pages.passes`). The runs are the kind's poll runs of the day that were not blocked and read the listing (`listing_read_at` set), in the order of `listing_read_at`, never of the run id, whose time is UTC. Each run joins the current pass; after it joins, the pass ends when the pass's own runs read the kind in full by R37's joining (a run without page records that ended with no error reads it on its own), or when this run recorded a page of the kind out of order, and the next run begins a new pass. The runs left at the end make the last pass, open. A poll run of a paged kind starts from the last pass (`pass_start`): when it is open, R37's start rule over that pass's runs alone (a resume at its furthest page, detours to its failed files' pages); otherwise, with no pass yet or the last one read in full or ended by a page out of order, a fresh pass from page 1 with no detour. So a page out of order costs one pass, not the day. A run that never read the listing read no page, so it can neither complete nor end a pass. A blocked run's pages, in order or not, are not seen by the passes, where R37's order check reads blocked runs' pages too: a block latches the chain, so the day's later runs are blocked as well. R37's functions (`read_in_full`, `start_for`, `unread`, `has_pages`) are unchanged and read the full kinds as before: each reads only the runs that cover the kind it is asked about, and only that kind's pages.
  - **The morning, from main and retry runs only.** The check judges a day's morning from that day's `main` and `retry` manifests alone (`check.MORNING`): a poll can stop on time with names listed and not yet stored, which a later poll takes, so a poll's names never reach the morning's `missing`, `listed` or `manifests`. `stored` counts every stored name, a poll's files included. R4, R31 and R35 to R37 read the same main and retry runs as before, so a poll's block never silences R35's or R37's reason.
  - **The update day.** While the poll switch is on, or when a check event asks for it (`"update_day": true`, the JSON value true and nothing else), the check of day D also judges D−1 (`check.judge_update_day`) for the chains whose `polled` is set, from every manifest of D−1, polls included, and D−1's stored names, and writes the result into D's check record as `update_day` (`day` and `chains`; null when not judged). Its alerts follow the morning's in the one email. For each chain:
    - `missing`: names a poll run of D−1 tried and failed that are still not stored and that no main or retry run of D−1 listed (those were judged by D−1's own check, never reported twice), as one alert: `<slug>: <n> update files a poll run tried on <day> and did not store: <up to ten names>.` (`update file` for one; beyond ten, `, and <n> more (the check record lists them all)` before the full stop). (Since ruling R40, the alert also names the day's `not_tried` names of each kind with no page records, in one sentence: `<slug>: <n> update files listed on <day> and not stored (<k> tried and failed, <m> never tried: …): <names>.`)
    - `failed`: the update kinds no pass of D−1 read in full, a day with no poll at all included, so a lost schedule shows, as one alert: `<slug>: no poll run read the Price and Promo lists in full on <day>.` (`the Promo list` for one kind, the kinds in `polled` order). None, and the record's `failed` null, when a poll run of D−1 was blocked: the stopped alert covers it, as R35 leaves a blocked retry's day to it.
    - Recorded, never emailed: `polls` (each poll run's id, kinds, error and blocked, and its counts of listed, stored, failed and not attempted names); `passes`, per kind: `complete` (the runs that read each complete pass, as `read_in_full` names them), `out_of_order` (the runs of each pass a page out of order ended unread) and `open` (the last pass's runs, and, with page records, what of the list it has not read, in `unread`'s words; null when the last pass is not open); `not_tried`, per kind, the distinct names any poll listed and never tried (`not_attempted`) that are still not stored and not `missing`: the measure of what the time rule costs (since ruling R40: the names, per kind and sorted, not a count, leaving out names a main or retry run of D−1 listed; emailed for a kind with no page records); and `by_hour`, per kind, D−1's stored files of the kind counted by the hour in their names (`collector.names.hour_of`: `"00"` to `"23"` from NCR's and Carrefour's `-YYYYMMDD-HHMMSS`, store 039's `-YYYYMMDDHHMM` and Shufersal's stamps; `"unknown"` where no hour can be read, never dropped).

- Ruling R40 (2026-11-08, the owner's request of 2026-11-07 and design `docs/unreached-names.md`, approved 2026-11-08; amends R39): a poll run of a listing that does not page, stopped on its own time check, lists the rest of that listing from memory, and the next morning's check emails each update file of the day that a poll listed and no run stored, tried or not. Where the design left room, the build decided (`docs/unreached-names-plan.md`, "Where the design leaves room, this plan decides"); those decisions are part of the rule below.
  - **The drain.** When a run's `error` is exactly the time stop (`stopped: under 90 s left`), its mode is `poll`, its listing was created and its adapter is not a `PagedSource`, the run asks the listing for its remaining rows until it ends. Each row goes through the take's classification and nothing else (`_listed`, shared with `_take`): a kind not asked for is skipped, a name of another day is counted in `other_days` once, a name already seen in the run is skipped, and any other name joins `listed`, and `not_attempted` unless it was stored before the run. No download, store, time check or page record follows. The manifest's `error` stays the time stop, and `unparsed` stays 0, as on every stopped run.
  - **Only that stop drains.** A main or retry run, a Shufersal run (its page records are what the resume and the joining read), a stop before the listing, and a stop for a block, an unreadable listing or a failed listing drain nothing: their manifests are what they were before this ruling.
  - **What the drain may meet.** The listing's end, or `OutOfTime`, ends the drain with what it had. A block latches the chain as the loop would (`blocked` set first, then the state; a poll's stopped email at once, R39), and the manifest carries the time stop and the block. Anything else means an adapter made a request after the stop: `error` becomes `unexpected error: <type>: <text>`, the exception is raised and the invocation fails, and the rows drained before it stay listed. A latch that cannot be written reads as in the loop (`latch not written: …`, raised).
  - **The rule for adapters.** An adapter that is not a `PagedSource` makes no request after its first row, or asks `short_of_time` before each one it must make (`collector.sources`). NCR's reads its whole directory and Carrefour's its one page before giving the first row, and a test of each pins it.
  - **The update day.** `not_tried` holds, per update kind, the names, sorted, not a count: names a poll listed and never tried that are still not stored, not in `missing`, and that no main or retry run of the day listed (judged by that day's own check, never reported twice). The `missing` alert takes, beside the names a poll tried and failed, the `not_tried` names of each kind with no page records that day, in one sentence for the chain: `<slug>: <n> update files listed on <day> and not stored (<k> tried and failed, <m> never tried: a poll stopped on time before reaching them): <up to ten names>.` (`update file` for one; `reaching it` for one never tried; a zero part left out; the names of both parts sorted together; beyond ten, `, and <n> more (the check record lists them all)`). No alert when both are empty. The record's `missing` still holds the tried-and-failed names. The `failed` alert is unchanged, so a day whose only poll stopped on time with names held gets both sentences.
