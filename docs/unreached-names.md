# A time-stopped run's unreached names (design)

Grade: production. The collector is live, and every file it stores is locked for ten years.
Status: draft of 2026-11-08, written by Fable 5.1; revised the same day after an Opus builder check (2 blocking, 8 should-fix, 13 notes, each checked against the code before it was folded in), which moved the recommendation from every run to poll runs only, added the rules for an error or a block met while the rest of a listing is read, and for Shufersal's untried names, and two questions (D and E). Approved by the owner on 2026-11-08 with questions B, A and E answered as recommended and D the other way (the manual polls run first, on q23's code); nothing built. The owner asked for this fix on 2026-11-07, after q23's final review found the gap: before the poll switch goes on, either the update day flags a chain whose day's last poll stopped on time, or the run counts what it held unreached, and either way without new requests to the portals. Every choice the owner has not made is marked "Call" and listed at the end, with the questions.

## Why

The run loop reads a listing one row at a time and downloads each file before asking for the next row (`src/collector/run.py:9-10`). After each row it checks the time, and with under 90 s left it stops before asking for the next one (`run.py:169-171`, `_check_time` at `run.py:290-292`; ruling R32, `MIN_TIME_LEFT` at `run.py:63`). So the rows the listing had not yet given are in none of the manifest's lists: not `listed`, not `not_attempted`. The module says so itself ("Names the listing had not yet given when the run stopped are in none of them: the retry run lists them", `run.py:38-39`), and [operations.md](operations.md), line 182, wrote it down at q23's build as a reading note. The one place a name can enter `not_attempted` is `_fetch`, when the time runs out between the loop's check and the download's (`run.py:248-253`), and it stops the run right after, so `not_attempted` holds at most one name a run. The tests pin today's behaviour: `tests/test_run.py`, `test_time_checked_after_a_download` (line 620: three rows, two given, `not_attempted` empty), `test_time_checked_between_listing_items` (608), `test_stops_before_timeout_and_records_not_attempted` (591), `test_out_of_time_in_a_download_fails_that_file_and_stops_the_run` (661) and `test_no_retry_under_ninety_seconds` (680); all five pass on this branch.

**The morning is covered, as far as the owner chose.** A run with no page records reads a kind in full only when it ended with no error (`src/collector/pages.py:77`), so a time-stopped main or retry run never counts as a full reading; a stopped main run's error is left to the retry, which lists the whole day again and skips what is stored (`src/collector/check.py:17-18`; `run.py:229-230`); a stopped retry is a failed run unless R36 excuses it (`check.py:237-263`). One narrow shape is excused on the four quick chains: R36's excuse holds when every name the retry listed was listed by a run that read the kind in full and nothing is missing (`check.py:254-263`); a retry that re-fetched the main run's failed names, stored them, and then stopped on time before reaching files published since the main's read listed only names the main listed, so it is excused, and the files it never reached are lost with no email. That is the cost R36 accepts in so many words ("a file a store publishes after the run that read the listing in full, which the stopped retry did not reach, is never collected and sends no email", [collector-plan.md](collector-plan.md), line 335, approved by the owner on 2026-11-04), and this note keeps it (section 4, Question B).

**The update day is not covered.** The check judges the day before from its polls (`check.py:311-337`; design [update-files.md](update-files.md), section 5; ruling R39). A kind fails only when no pass read it in full (`check.py:319-320`); for a chain without page records a pass is any poll that ended with no error (`pages.py:77`, `pages.py:146-164`), so one clean poll at 12:20 satisfies the day. `not_tried` counts the names in `not_attempted` that are still not stored (`check.py:318`, `333`), which is at most one a stopped poll. A day whose last poll of a kind stopped on time, after an earlier clean poll, loses every file that poll held unreached, with no email and almost nothing in `not_tried`. That breaks the design's own goal for these chains ("every update file in the day's listing at the last poll of the day is stored", [update-files.md](update-files.md), line 32).

**What is knowable without a request.** The three NCR chains' adapter logs in, reads the whole directory, checks every name and only then gives the first row (`src/collector/sources/ncr.py:24-27`, `73-80`: a list, then `yield from listed`); Carrefour's reads its one page the same way (`src/collector/sources/carrefour.py:14`, `38-45`). Both are proved: `tests/test_ncr.py:195-201` asserts no request until the first row is asked for and the whole listing read by then, and `tests/test_carrefour.py:120-127` the same with the listing then read to its end and the one request still the only one. So once a run of these four chains has its first row, the rest of the listing sits in the generator's memory, and reading it on costs nothing. Shufersal's listing is the opposite: it yields a page's rows and requests the next page only when asked for the row after them (`src/collector/sources/shufersal.py:86-93`), each request after the run's time check (`shufersal.py:257-258`), so after a time stop the only rows in memory are the rest of the page in hand, and the pages after it are not knowable. For Shufersal the page records already say what was not read (`pages.py`, `unread`, line 85). Carrefour is not an NCR chain (`ncr.py:1`; `src/collector/chains.py:53`), though the brief for this note said so; nothing below depends on it.

**Where else a run stops on time, checked.** Before the listing (`run.py:165`): nothing read, nothing held. Inside an adapter's own request, raised as `OutOfTime` (`run.py:210-211`): NCR's listing answers (`ncr.py:136-137`), which happen before the first row, so the generator ends with nothing held, and Shufersal's pages, between pages, so nothing is held either. In a download (`run.py:258-260`): only Shufersal's refresh of an expired link (`shufersal.py:120-125`), a paged source. So the loop's check and `_fetch`'s are the two places a run stops with rows in hand, and both are in `_Run.collect`'s one `except _Stop` (`run.py:173-174`). Manual runs cannot re-fetch a past day (the day is always the invocation's, `src/collector/handler.py:129`; [update-files.md](update-files.md), "Risks kept"), so nothing below is a recovery path: it is knowing.

## Goals

- A manifest of a poll run of Rami Levy, Osher Ad, Carrefour or Yochananof that stopped on time names every file of its day it listed and did not reach.
- The update day's `not_tried` is the true count of what the time rule cost, and a day that lost files is not read as clean.
- Not one request more to any portal.

## Non-goals

- No change to the 90 s rule, the schedules, the poll switch or the passes rule (R39).
- No change to the morning's runs, their manifests or the morning judgement (the design's non-goal, [update-files.md](update-files.md), line 40, and R36's accepted cost, kept: Question B).
- No change to Shufersal's listing, page records, resume (q21, [shufersal-resume.md](shufersal-resume.md)) or page tries (q24, [shufersal-page-retry.md](shufersal-page-retry.md)); its update day waits for its polls ([update-files-plan.md](update-files-plan.md), Task 10), under one rule written here so a builder need not guess (section 3, Question E).
- No sweep of the day before (the design's non-goal stands); no re-fetch of a past day.
- No new manifest field and no new alert kind.

## Anti-goals

- A request made after the time rule said stop, or a manifest written later than today (R38's invariant: at least about 30 s left).
- An email for a poll that stopped on time when nothing was lost: a later poll took what it held.
- A loss reported twice: by the morning's check and the update day's, or by two update-day alerts.
- The morning judgement's rulings (R4, R31, R35 to R37) changed in code, text or inputs.
- A drained row doing anything a taken row does beyond being counted: no download, no page record moved.
- A fault met while the rest of a listing is read that leaves the manifest reading as a plain time stop.

## The options

**A. The run counts what it held.** After a time stop, a run whose listing is not paged reads the rest of the listing from memory, taking nothing, and records each row of its day and of a kind it asked for as a taken row minus the download: in `listed`, and in `not_attempted` when not stored before. For the four quick chains that is the whole listing as it stood when the run read it, so the manifest is complete and the update day's existing arithmetic (`not_tried` = names in `not_attempted` still not stored, `check.py:318`) becomes exact: a name a later poll stored drops out, a name no poll stored is a file lost. What it cannot know: files published after the run read the listing (the next poll's, or nobody's after the day's last poll: the design's risk, [update-files.md](update-files.md), line 232) and, for Shufersal, anything past the page in hand. Two reaches: **(a) poll runs only**, which is what the owner's requirement is about, leaves every main and retry manifest, the morning judgement and its emails exactly as today, and keeps R36's accepted cost; **(b) every run**, which also completes the morning's manifests and closes R36's narrow shape, at the price of new morning emails and of reversing that accepted cost (Question B).

**B. The check flags a chain whose last poll of a kind stopped on time.** From the manifests already written: the last poll of the day that covers the kind (by `listing_read_at`) has `error` equal to `OUT_OF_TIME`. No run changes. What it cannot know: whether anything was lost. A poll stops on time only while downloading, but the rows it had not yet reached can be names already stored (skipped in microseconds, `run.py:229-230`), names of another day, or new files: B emails on the first two as on the third, which the design's anti-goal forbids ("a poll stopped on time … must stay quiet", [update-files.md](update-files.md), line 51), and it says nothing about an earlier poll whose unreached names no later poll took. For Shufersal B is the only signal there can be, and its record already carries it: each poll's `error` and the open pass are in `update_day` today (`check.py:327-331`, `348-349`).

**C. Both.** A for the count; B as the alert's trigger. B adds nothing A does not know better for the quick chains, and for Shufersal the trigger is a question for Task 10, where the passes are designed.

**Recommendation: A, poll runs only.** It answers the owner's requirement in the form that keeps the design's email rule intact (an email only for data lost), makes the record the design promised to read in the first week true (`not_tried`, rollout step 2), costs no request because the four adapters' listings are already whole in memory after their first row, and reverses no decision the owner has made but call 7, and that only if the owner says so (Question A). Every run is one condition less in the code and is offered as a queue item of its own (Question B). Call 1.

## What changes

### 1. The run loop: after a poll's time stop, the rest of an unpaged listing is read from memory

When `_Run.collect` catches `_Stop` (`run.py:173-174`) and four things hold, the run asks the listing for its remaining rows until it ends: the result's `error` is exactly `OUT_OF_TIME` (`run.py:65`; R36 matches the same text); the run's mode is `poll` (`RunResult.mode`, as `_paged` reads it at `run.py:184`; Call 2); the listing was created (a stop before it, `run.py:165`, has none); and the source is not a `PagedSource` (`src/collector/sources/__init__.py:100`; the same test the run uses at `run.py:180-181`). Each row goes through the take's classification and nothing else (`run.py:219-230`, factored out of `_take` so both paths share it: Call 3): a kind not asked for is skipped; a name of another day is counted in `other_days` once; a name seen already in this run is skipped; otherwise the name joins `listed`, and joins `not_attempted` unless it was stored before the run. No download, no store, no state write, no time check. A `PagedSource` is not drained, even its page in hand: its page records (`taken_through`) are what the resume and the joining read, and a page half-drained would either move them or leave `listed` and the records disagreeing (Call 5). A stop for any other reason (a block, an unreadable listing, a failed listing) drains nothing: the chain is latched or the run has failed, and the `stopped` or `failed` alert covers the day (Call 4). The manifest's `error` stays `OUT_OF_TIME`; `unparsed` stays 0, as on every stopped run, though the listing has now been read to its end (R13's rule, `run.py:75-76`, reworded on build; Call 6). The drain runs over at most the directory's few thousand entries in memory (2,362 on 2026-11-01, [update-files.md](update-files.md), line 26), milliseconds, before the manifest write in `collect_chain`'s `finally` (`run.py:119-120`), so R38's margin for the manifest stands.

**What the drain may meet, and what it does then (Call 11).** An adapter that is not paged makes no request after its first row (the rule for adapters, section 2), so the drain expects rows, the listing's end, or `OutOfTime`, the one thing an adapter that honours the lent time check (`sources/__init__.py:7-10`) can raise with no time left; `OutOfTime` ends the drain with what it had. Anything else means an adapter made a request after the stop, which no adapter does today, and it must not pass as a time stop: `collect_chain` writes `unexpected error: <type>: <text>` only for a first error (`run.py:115-118`, `if result.error is None`), so without a rule a fault in the drain would leave the manifest reading `stopped: under 90 s left`, the text R36 matches exactly and the passes read as a mere stop. So: a `Blocked` from the listing during the drain latches the chain as the loop would (`_latch`, `run.py:302-313`: `blocked` set first, the state written, and a poll's stopped email at once as today, `handler.py:160-161`), and the drain ends there, catching the latch's `_Stop` itself (a `_Stop` raised inside `collect`'s handler would otherwise escape to `collect_chain`, which keeps the error set and fails the invocation); the manifest then carries the time stop and the block, and the stopped alert covers the day. Any other exception replaces `error` with `unexpected error: <type>: <text>`, the text `collect_chain` would have written, and is raised, so the invocation fails and the manifest says why; the rows drained before it stay listed. The `_Stop` the drain can meet is the latch's and no other: the classification raises none.

### 2. The manifest, and a rule for adapters

No new field. For a poll run of an unpaged listing, `listed` now holds every name of the day and the kinds asked for that the listing gave, a stopped run included; `not_attempted` every such name not stored before the run and never tried, which is the meaning both already have (`run.py:36-39`); `other_days` counts the rest of the listing's other-day names too (Call 7); `not_attempted` stays a subset of `listed`. For a main or retry run, and for every Shufersal run, the lists are what they are today: a stopped run's `listed` ends where it stopped. The module docstring says both (its sentence at `run.py:38-39` on the names the listing had not yet given is rewritten by mode and by paging). Manifests written before this change read as before: no reader changes what it reads, and the handler's summary line already logs the `not_attempted` count (`handler.py:162-164`). `src/collector/sources/__init__.py` gains the rule the drain rests on, beside the time-check contract at lines 7 to 10: an adapter that is not a `PagedSource` makes no request after its first row, or asks `short_of_time` before each one it must make; the run reads such a listing on after a poll's time stop. The NCR and Carrefour adapters keep it today (section "Why"), and a test per adapter pins it (section "Tests and mutations").

### 3. The check: the update day

`_judge_updates` (`check.py:311-337`) changes in two lines and, on the owner's word, a third:

- `untried` also leaves out the names a `main` or `retry` run of that day listed (`listed_by_morning`, `check.py:316`), as `unstored` does (`check.py:317`): those were judged at that day's 11:48 and are never reported twice (Call 8). Today `untried` subtracts only the stored names and `unstored` (`check.py:318`).
- `not_tried` holds the names, per kind and sorted, not a count (Call 9): the count is their length, and an alert or a reader needs the names. No code reads `update_day` (the basket reads each manifest's `files` with outcome `stored`, `src/basket/record.py:156-165`; `scripts/` only copies), so the shape can change; a check record written before this deploy by a manual check that asked for the update day (`"update_day": true`, `handler.py:188-190`; the scheduled check writes null while the switch is off, `check.py:134-135`) holds counts, write-once, and is read by eye either way (Question D).
- **Question A for the owner.** The design's call 7 (owner, 2026-11-06) says `not_attempted` names are counted, not emailed, on the ground that a slow Shufersal evening leaves such names on the day's last run ([update-files.md](update-files.md), line 126; call 7 at line 219; `check.py:91-94`). That ground does not hold for the four quick chains: their polls are sized to finish (300 files in 5 to 7 minutes, [update-files.md](update-files.md), line 79), their listings are whole, and a name in `untried` after this change is a file of the day that no run stored: data lost, which is what the design says an email is for (line 35). Recommended: the untried names join the chain's `missing` alert, one alert per chain, one sentence, the two counts apart, the names once (the union of the two disjoint sets, sorted together): `<slug>: <n> update files listed on <day> and not stored (<k> tried and failed, <m> never tried: a poll stopped on time before reaching them): <up to ten names>.` (`update file` for one; a zero part left out; beyond ten, `, and <n> more (the check record lists them all)` as today, `check.py:230-234`). This sentence replaces today's (`check.py:360-362`) on every such day, a day with no untried name included. No alert when both parts are empty. The `failed` alert is unchanged, so a day whose only poll stopped on time gets `failed` (no pass read in full) and, when it held names, `missing`, two sentences in the one email, as a morning does today. **Shufersal's rule, so Task 10 need not guess:** the untried names join the alert only for a kind with no page records that day (`not has_pages(manifests, kind)`, `pages.py:127`, the test `_not_read_in_full` and the passes record already use to tell the two apart, `check.py:308`, `349`); a paged kind's untried names stay counted, call 7 as it stands, until Task 10 decides (Call 10, Question E). `_judge_updates` has no chain or page branch today, and Shufersal is left out only because its `polled` is empty (`chains.py:49-50`, `handler.py:188-189`), so without this line Task 10's first `polled` would email Shufersal's untried names. If the owner keeps call 7, only the two record changes above are built, and the email texts stay word for word.

### 4. The check: the morning

Exactly as today: the morning reads `main` and `retry` manifests (`check.py:141`), none of which changes, so `missing`, R4, R31 and R35 to R37 have the same inputs, code and text. R36's accepted cost stands on the quick chains ([collector-plan.md](collector-plan.md), line 335; "Why" above): a stopped retry's unreached files stay unlisted and silent. This note names it as a cost kept, not an oversight. What draining every run would change instead is in Question B.

### 5. Shufersal: nothing moves

A `PagedSource` is not drained, so a Shufersal run's `listed`, `not_attempted`, `pages`, `taken_through` and `timeouts` are exactly what they are today, and so are `start_for`, `pass_start`, `read_in_full`, `passes` and `unread` (`pages.py`), the one-page overlap, the detours, the step-back and the tries. The four replay tests (`tests/test_replay.py:99`, `225`, `325`, `375`; Shufersal only, `test_replay.py:24`) pin it. Shufersal's update day keeps its gap until its polls are designed (Task 10): there, "the day's last pass is open" is the only signal possible, and whether it emails is that design's question; section 3's `has_pages` line keeps call 7 true for it in code meanwhile (Question E).

### 6. Not affected, checked

The basket reads each manifest's `files` with outcome `stored` and nothing else (`src/basket/record.py:156-165`); `coverage` reads stored names (`check.py:370-384`); `read_in_full` is unchanged because `error` stays set on a stopped run (`pages.py:77`); `scripts/sync.sh` copies manifests; the replays are Shufersal's. None reads `listed`, `not_attempted` or `not_tried`.

## Cost

$0.00 a month beyond [update-files.md](update-files.md), section 6 ([operations.md](operations.md), "Cost"): no portal request; no new S3 request (the manifest is one put as today); Lambda time in milliseconds inside a run that has already stopped. The one measurable change is a stopped poll's manifest: an unstored drained name is written twice, in `listed` and in `not_attempted`, at about 51 bytes a name a list as the manifest is written (`indent=1`, 45-character NCR names), so a poll that held a whole Rami Levy day of update names, about 2,200 (1,200 to 1,400 `Price` and 400 to 800 `Promo`, [update-files.md](update-files.md), section 6), writes about 225 KB more; the check record carries the same names once more. A few hundred KB on the rare stopped poll, locked for ten years, rounds to cents at year ten.

## Tests and mutations

Test-first; test data never reads the clock (`tests/test_run.py`'s `Clock` and `FakeSource`, lines 81 to 153; `collect` at line 168 runs as `main` unless told otherwise, and the `POLLING` chain fixture carries `polled`).
