# Resolved on 2026-11-25 from the packages uploaded before 2026-10-25, a month earlier:
#   pip install --uploaded-prior-to=2026-10-25 dbt-core==1.12.6 dbt-duckdb==1.11.0 duckdb==1.5.6
# Installed with these commands (in CI the same, the environment made by its Python 3.13's python -m venv):
#   python3.13 -m venv .venv-dbt
#   .venv-dbt/bin/pip install --no-deps packaging==26.3
#   .venv-dbt/bin/pip install --no-deps --no-build-isolation -r requirements-dbt.txt
#   .venv-dbt/bin/pip check
#
# One pin fetches from outside PyPI. dbt-core-experimental-parser 2.0.8, which dbt-core 1.12.6 requires, is a
# 4,776-byte source package on PyPI (SHA-256 35b7760967f9542fd0b1a3cd742ffd24e8e08a18473a84a891a3bc8a9d6b2910). Its
# build downloads a compiled wheel from dbt's GitHub release v2.0.8 (published 2026-10-14) and refuses it unless its
# SHA-256 matches the one the package carries, in _dbt_sa_build/assets.json: for macOS on arm64,
# 00f3ec35d555f6a4e3333b943011b1fdc99606112c6f3d7291c2809ae2f86c5c; for Linux on x86_64,
# 2186d331522b2a8a0f09d2f5c81ff5f1a433160ad7cd212906dccc0d4951d2a1. That build needs packaging, so packaging goes in
# first and the build is not isolated: an isolated build would fetch packaging unpinned. dbt runs that parser only
# when the v2 parser is asked for (--use-v2-parser, off by default, or its project flag or variable), which this
# project never does.
